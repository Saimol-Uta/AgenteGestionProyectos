# H5 API integration contract

Status: T1–T5 backend and frontend are implemented and integrated; controlled-fixture HTTP/browser journeys passed. The complete authentic historical browser demonstration and native review remain pending (see the task log). Base `/api/v1`. Spanish UI; technical identifiers retain domain values. No external writes are exposed.

## Shared conventions

- Paginated lists: `{items: T[], total: number, page: number, page_size: number}`. Query `page=1&page_size=25`, maximum 100.
- Errors: `{error: {code: string, message: string}}`; 422 validation errors must be understandable.
- ISO timestamps, configured timezone `America/Guayaquil`; null means unknown, never zero.
- GET has no inference, remote calls, schema changes, snapshot writes or job creation.
- The browser uses relative `/api/v1` via same-origin Vite proxy. No provider credentials.
- `GET /system/health`: `{status, version, external_writes_enabled: false}`.
- `GET /auth/session`: `{authenticated: boolean, actor: string|null, csrf_token: string|null, capabilities: string[], login_available: boolean}`. Public consultation is anonymous and read-only (`authenticated=false`, `actor=null`, no capabilities); it is not a privileged authenticated user. A verified operator reports `analysis:prepare` and `analysis:confirm` only when server opt-in and configured-project scope are both present; these capabilities do not authorize external writes.
- `POST /auth/login`: `{token: string}` verifies an independently provisioned backend operator token (not a provider key); sets HttpOnly/SameSite session cookie and returns the session DTO (never the submitted token). The frontend keeps only the returned session/CSRF in memory, never the token. A verified session reports `operator_session` and only the additional server-enabled, in-scope capabilities described above; none is authority for external writes.
- `POST /auth/logout`: revokes session, requires `X-CSRF-Token` and the exact allowed Origin. State-changing endpoints require the verified session and CSRF; no client role/actor accepted as authority. Read-only local consultation works without privilege. The session cookie is HttpOnly, SameSite=Strict, scoped to `/api/v1`, expires at the server TTL and is process-local/revocable; run one Uvicorn worker unless a shared session store is later added. Sessions are invalidated on restart. A verified operator session grants no external-write capability.
- The separately provisioned `H5_OPERATOR_TOKEN` must be at least 32 characters; it is accepted only in the login JSON body and is never returned or persisted. `H5_ALLOWED_ORIGINS` and `H5_ALLOWED_HOSTS` are exact comma-separated allowlists; `H5_SESSION_TTL_SECONDS` and `H5_SESSION_COOKIE_SECURE` configure cookie policy. `H5_ANALYSIS_ENABLED` is false by default and `H5_WEB_JOBS_DB_PATH` selects the separate local analysis/manual-cycle job ledger. `AGENTE_CONFIG_PATH`, `AGENTE_DB_PATH`, `AGENTE_RUNS_DIR`, and `H5_OUTBOX_DIR` configure backend paths; `.env` files are not loaded. Without `AGENTE_CONFIG_PATH`, project metadata is read from `config/hormigestion.yaml` using only allowlisted project, timezone, scheduling and storage fields.

## Tracking endpoints (T1/T2)

- `GET /projects`: paginated Project `{id, name, source_mode, latest_capture_at: string|null, latest_run_id: string|null, latest_run_status: string|null, summary: TaskPlanSummary|null}`. Actual configured/stored projects only.
- `GET /projects/{id}`: Project.
- `GET /projects/{id}/summary?capture_id=...`: TaskPlanSummary, preserving the existing Pydantic model's fields: project_id, capture_id, captured_at, cutoff_datetime, total_tasks, included_tasks, completed_tasks, progress_percentage, state_counts, overdue_count, due_soon_count, blocked_count, unknown_count, contradictory_count, overdue_task_ids, due_soon_task_ids, blocked_task_ids, unknown_task_ids, contradictory_task_ids, identified_risks.
- `GET /projects/{id}/tasks`: paginated items retain the domain `TaskDetailView` shape. Query `capture_id`, `q`, `state`, `assignee_id`, `list_name`, `critical_only`, `overdue_only`, `due_soon_only`, `sort=due_date|title`, `direction=asc|desc`; the detail-only envelope is not repeated for every list row.
- `GET /projects/{id}/tasks/{task_id}?capture_id=...`: flattened `TaskDetailView` fields plus `evidence` and `history`. Task states retain the domain's Spanish values (`pending`, `en_curso`, `completada`, `bloqueada`, `desconocido`).
  - `evidence` is always an array (empty when unavailable) of allowlisted `{provenance, category, summary}` DTOs. Provenance contains only safe identifiers/source, timestamp, and validated optional repository, commit, relative file, diff-side, line, and external-ID fields. Arbitrary evidence payloads and artifact contents are never returned; secret-like text in summaries is redacted.
  - `history` is always an array (empty when no prior comparable capture is available) of canonical `TaskChange` fields plus nullable `observed_at`, `capture_id`, `previous_capture_id`, and `current_capture_id`. These timestamps/refs describe the compared stored captures, not an independently attributed event. `actor` remains `null`; no person is inferred.
  - Frontend models may treat `evidence` and `history` as optional for forward/backward compatibility and must render only returned items; no evidence or timeline event is synthesized.
- `GET /projects/{id}/history`: paginated capture metadata with `{capture_id, captured_at, summary}`.
- If the database is missing, configured projects remain listed with null capture/summary metadata and task/history lists are empty; GET never creates a database. An explicit summary/detail/compare request without a matching capture returns a standardized 404.
- `GET /projects/{id}/compare?before=CAPTURE&after=CAPTURE`: existing TaskSnapshotComparison JSON.

## T3 run, quality and executive contracts (API implemented; frontend integration pending)

These wire shapes are stable for frontend integration. Every DTO is a safe projection of persisted data; fields unavailable in old/incomplete runs are `null`, `unknown`, or empty arrays with an explicit availability field. No response contains raw LLM payloads or arbitrary artifact paths. Candidate findings are not confirmed defects unless persisted verifier evidence says so.

### Persisted run queries

- `GET /runs?project_id=ID&page=1&page_size=25` → `Page<RunSummary>`; `project_id` is required and results are newest-first.
- `GET /runs/{run_id}` → `RunDetail`.
- `GET /runs/{run_id}/stages` → `{run_id, items: StageView[]}`. The five known stages are `source_collection`, `monitoring`, `quality`, `verifier`, and `report`. A persisted `skipped` status means explicitly omitted; an absent stage record is represented as `status: "unknown", recorded: false`, never inferred as skipped/completed.
- `GET /runs/{run_id}/findings?page=1&page_size=25` → `Page<FindingSummary>`.
- `GET /runs/{run_id}/findings/{finding_id}` → `FindingDetail`, including persisted verification, safe evidence references and an optional persisted-snapshot code excerpt.
- `GET /runs/{run_id}/evidence?page=1&page_size=25` → `Page<EvidenceSummary>`.

`RunSummary` fields: `run_id`, `project_id`, `status` (`queued|collecting|analyzing|awaiting_human|completed|needs_attention|failed|cancelled|unknown`), `created_at`, `updated_at`, `snapshot_id`, `duration_seconds: number|null`, `is_simulated: boolean|null`, and `report_id: string|null`. `RunDetail` adds only `error_code: string|null`; free-form exception text is not returned.

`StageView` fields: `stage_name`, `status` (`pending|running|completed|skipped|failed|needs_attention|unknown`), `recorded`, `duration_seconds: number|null`, `completed_at: string|null`, `providers: ProviderAttempt[]|null`, `result_summary: string|null`, and `error_code: string|null`. Provider/model/status/duration values come from persisted LLM attempts; `null` means no recorded attempt, not zero work. Errors use safe codes, not raw exception messages.

`FindingSummary` fields: `finding_id`, `run_id`, `category: string|null`, `severity: string|null`, `rule_id: string|null`, `file_path: string|null`, `line: number|null`, `commit_sha: string|null`, `confidence: number|null`, `candidate: true`, and `verification_status` (`pending|confirmed|rejected|insufficient|unknown`). Values not persisted by legacy finding rows remain null. `FindingDetail` adds `claim: string|null`, `suggested_fix: string|null`, `evidence_ids: string[]|null`, `verification: {verdict, reason, verified_by, evidence_ids}|null`, `evidence: {availability: "available"|"unknown", items: EvidenceSummary[]}`, and `code_excerpt: CodeExcerpt|null`.

`EvidenceSummary` fields: `id`, `source`, `timestamp: string|null`, `repository: string|null`, `commit_sha: string|null`, `file_path: string|null`, `lines: number[]|null`, `category: string|null`, and redacted `summary`. Its raw payload is never returned. `CodeExcerpt` fields: `evidence_id`, `file_path`, `lines`, `content`, `evidence_scope`, `is_partial`, and `redacted`. An excerpt is returned only when its persisted evidence, finding location, commit, and stored snapshot snippet agree. It is partial unless the stored `CodeDiffSnippet` itself proves complete-file coverage; no source fetch or artifact-path lookup is performed.

### Quality, policies and executive dashboard

- `GET /projects/{project_id}/quality` → `QualitySummary`: `project_id`, `run_id: string|null`, `stage_status: StageStatus|null`, `availability: "available"|"unknown"`, `finding_counts: {candidate, confirmed, rejected, insufficient, pending, unknown}|null`, and `ci: {id, workflow_name, commit_sha, status, total_tests: number|null, failed_tests: number|null, coverage_percentage: number|null, timestamp: string|null}|null`. Missing CI/coverage is null/unknown, never zero.
- `GET /projects/{project_id}/policies` → `{project_id, run_id: string|null, availability: "available"|"unknown", items: PolicyResult[]}`. Each actual persisted evaluation is `{rule_id, description, status: "pass"|"fail"|"unknown", mandatory, observed_value: scalar|null, reason: string|null}`. Missing evaluations are not synthesized as passing or failing Q1/Q2/Q3 rows.
- `GET /projects/{project_id}/executive-summary` → `ExecutiveSummary`: `{project_id, capture_id: string|null, task_summary: TaskPlanSummary|null, capture_series: [{capture_id, captured_at, progress_percentage: number|null, total_tasks, completed_tasks, state_counts}], quality: QualitySummary|null, policies: PoliciesSummary, latest_report: {report_id, run_id, cutoff_datetime, recommendation, human_decision, summary}|null, runs: {total, by_status, series: [{run_id, created_at, status, duration_seconds: number|null}]}}`. Capture/run series contain stored records only; backend domain metrics remain authoritative for critical counts and progress.

### Controlled asynchronous analysis

- Capability is opt-in: `H5_ANALYSIS_ENABLED=false` by default. Verified `/auth/session` reports `analysis:prepare` and `analysis:confirm` only when server opt-in is enabled and the session has configured-project scope. Projects discovered only from storage are never executable.
- `POST /projects/{project_id}/analysis/prepare` requires a verified operator session, exact allowed `Origin`, CSRF token, and JSON `{"request_analysis": true}`. It performs configuration/source checks without starting an agent, network probe, or job. Response `AnalysisPreparation`: `{preparation_id, project_id, expires_at, configuration_fingerprint, eligible, capabilities, preflight: {source_mode, configuration_status, checks: [{code, status}]}, remote: {required, server_allowed, availability: "not_checked", providers: [{stage, provider, model, transport, credential_status}]}}`. Credential presence is configuration metadata only; it does not assert remote availability.
- `POST /projects/{project_id}/analysis/confirm` requires the same session/Origin/CSRF checks and `Idempotency-Key` header. Required JSON: `{"preparation_id": string, "configuration_fingerprint": string, "confirm_analysis": true, "remote_consent": boolean}`. `confirm_analysis` is the affirmative request to run; `remote_consent` is a separate affirmative permission for configured remote sources/providers. Remote LLM use additionally requires the server-side `allow_remote_ai` configuration. Changed configuration/fingerprint, missing consent, unconfigured scope, queue saturation, or disabled opt-in creates no job.
- Accepted confirmation returns HTTP 202 `{job: AnalysisJob, reused: boolean, poll_url: string, poll_after_ms: number}`. `GET /analysis/jobs?project_id=ID&page=1&page_size=25` and `GET /analysis/jobs/{job_id}` poll the durable local web-job ledger and require a verified in-scope operator session. `AnalysisJob` is `{job_id, project_id, status: "queued"|"running"|"completed"|"failed"|"interrupted", created_at, updated_at, run_id: string|null, error_code: string|null, remote_consent: boolean, stage_progress_available: boolean}`. `completed|failed|interrupted` are terminal. `stage_progress_available` is true only when the mapped run belongs to the project and persisted stage records exist; otherwise it is false, never a percentage estimate.
- One worker and a finite queue are used; an idempotency key replay with the same request returns the original job, while conflicting reuse or an active duplicate is rejected. Job state and run mapping live in a separate local ledger (`H5_WEB_JOBS_DB_PATH`, default `.runtime/h5-web-jobs.sqlite`), not in the tracking DB. App import and GET are inert. After process restart, work is not resumed; stale active jobs are exposed as interrupted and persisted as interrupted on the next protected control-plane write. Job errors expose safe codes only.
- The existing orchestrator and read-only source composition are invoked only by a confirmed job. Tests inject an executor/fake ports; no tests perform external calls. No Trello write adapter is constructed and external mutations remain disabled.

These T3 API implementations and frontend views are available. Actual HTTP/browser integration is checked separately from intercepted frontend tests; do not infer absent values or substitute client-calculated metrics.

## T4/T5 governance, reports, audit, schedule and configuration contracts

Status: **T4/T5 handlers and frontend integration implemented; controlled-fixture HTTP/browser governance, reporting, scheduling, audit and configuration checks passed.** The paths, names, request bodies, capabilities, error codes and terminal states below are the implemented integration contract. `Page<T>` uses the shared pagination shape above; collection DTOs additionally carry `availability: "available"|"unknown"` so a missing legacy table is not presented as a known empty result. All timestamps are ISO-8601 and displayed in the configured timezone. GET and import stay read-only/inert. No endpoint enables or invokes external Trello writes; `/system/health.external_writes_enabled` remains false.

### Proposals and separate review / dry-run authorization

- `GET /projects/{project_id}/proposals?page=1&page_size=25&review_status=...` → `ProposalCollection`: `{availability, items: ProposalSummary[], total, page, page_size}`. `review_status` is optional `pending|approved_offline|rejected`.
- `GET /projects/{project_id}/proposals/{proposal_id}` → `ProposalDetail` (one `ProposalSummary` plus `decision_history_availability: "available"|"unknown"`, `dry_run_availability: "available"|"unknown"`, `decision_history: ProposalDecisionEvent[]` and `dry_runs: ProposalDryRun[]`). An unknown proposal or a proposal outside the URL project is a 404.
- `ProposalSummary` is an allowlisted projection: `proposal_id`, `project_id`, `task_id`, `capture_id`, `field`, `current_value`, `proposed_value`, `rationale`, `expected_impact`, `evidence: ProposalEvidence[]`, `proposal_body_sha256`, `version: number|null`, `technical_eligibility: "eligible"|"ineligible"|"unknown"`, `technical_errors`, `freshness: "current"|"stale"|"unknown"`, `review_status: "pending"|"approved_offline"|"rejected"|"unknown"`, `authorization_status: "not_authorized"|"authorized_dry_run"|"denied"|"revoked"|"unknown"`, and `execution_status: "not_executed"|"EXECUTED"|"ALREADY_APPLIED"|"DENIED"|"CONFLICT"|"FAILED"|"unknown"`. Values are only the stored field-specific proposal values. `ProposalEvidence` is `{evidence_id, category, summary}` with redaction; no raw evidence payload is returned. `ProposalDecisionEvent` is `{event_id, decision: "approve_offline"|"reject"|"authorize_dry_run"|"deny"|"revoke", version: number, recorded_at: string|null, actor_id: string|null, actor_provenance: "asserted_offline"|"unknown"}`. The domain's `OfflineActorClaim` remains unverified: historical core events have `actor_id: null`; only a separate linked web security-audit event may name the server-configured local actor.
- Mutations require a verified in-scope local session, exact allowed `Origin`, `X-CSRF-Token`, a valid `Idempotency-Key`, and server opt-in `H5_GOVERNANCE_ENABLED=false` by default. Public request data never supplies actor, role, auth token, project scope, capture or body hash authority. Each web proposal mutation and its linked verified-session security-audit event commit in one SQLite transaction; an audit-write failure rolls back the proposal decision or dry-run receipt.
- `POST /projects/{project_id}/proposals/{proposal_id}/review` JSON: `{decision: "approve"|"reject", expected_version: number, proposal_body_sha256: string, capture_id: string}`. Response: `{proposal: ProposalDetail, reused: boolean, audit_event_id: string}`. This changes only the append-only offline review ledger; approval is neither report approval, execution authorization nor a live mutation.
- `POST /projects/{project_id}/proposals/{proposal_id}/dry-run-authorization` JSON: `{authorize: true, expected_version: number, proposal_body_sha256: string, capture_id: string}`. Response is the same mutation envelope. This is a distinct, version-bound permission to simulate the immutable proposal only.
- `POST /projects/{project_id}/proposals/{proposal_id}/dry-runs` JSON: `{expected_version: number, proposal_body_sha256: string, capture_id: string, permission_event_id: string}`. `Idempotency-Key` determines the server-side request ID. Response: `{dry_run: ProposalDryRun, reused: boolean, audit_event_id: string}`. `ProposalDryRun` is `{request_id, status: "SIMULATED"|"denied", reasons: string[], field: string|null, before: string|array|null, after: string|array|null, recorded_at, execution_status: "not_executed", live_state_changed: false, real_execution_allowed: false}`. A simulation never reads a live provider, writes Trello, or changes task state. `technical_ineligible`, stale capture/version/body, revoked permission and duplicate-key conflicts fail closed.
- Stable errors include `gobernanza_no_habilitada`, `proyecto_fuera_de_sesion`, `propuesta_no_encontrada`, `version_obsoleta`, `vinculo_de_propuesta_invalido`, `permiso_de_simulacion_requerido`, and `idempotencia_conflictiva`.

### Reports, protected human decisions and downloads

- `GET /projects/{project_id}/reports?page=1&page_size=25&decision=...` → `ReportCollection`: `{availability, items: ReportSummary[], total, page, page_size}`; optional `decision` is `pending|approved|rejected|changes_requested|postponed`.
- `GET /projects/{project_id}/reports/{report_id}` → `ReportDetail`, including persisted `decision_history: ReportDecisionEvent[]` and sanitized `markdown_text: string|null`.
- `ReportSummary` fields: `report_id`, `project_id`, `run_id: string|null`, `report_version`, `created_at`, `cutoff_datetime`, `recommendation`, `human_decision`, `decision_reason: string|null`, `decision_timestamp: string|null`, `summary`, `metrics: ReportMetrics`, `risk_task_ids: string[]`, `recommendations: string[]`, and `policy_results: PolicyResult[]`. `ReportMetrics` carries only persisted deterministic counts and nullable progress: `total_cards`, `included_cards`, `completed_cards`, `progress_percentage`, `overdue_card_ids`, `due_soon_card_ids`, `blocked_card_ids`, `unknown_card_ids`, `contradictory_card_ids`. Candidate findings remain candidates; no provider payloads, raw evidence, arbitrary paths or inferred CI/coverage values are included. A report is returned only when its stored project/report/run bindings validate.
- `ReportDecisionEvent` is `{decision_id, report_id, run_id: string|null, decision, reason: string|null, recorded_at, actor_id: null, actor_verification: "unknown"}`. The core history does not persist an authenticated human identity; a successful web decision response separately supplies `audit_event_id` linking to its verified local-session security event.
- `POST /projects/{project_id}/reports/{report_id}/decision` requires a verified in-scope session, `Origin`, CSRF, `Idempotency-Key`, and server opt-in `H5_REPORT_DECISIONS_ENABLED=false` by default. JSON: `{expected_report_version: number, expected_human_decision: "pending", decision: "approved"|"rejected"|"changes_requested"|"postponed", reason: string|null}`. Response: `{report: ReportDetail, decision_event: ReportDecisionEvent, reused: boolean, audit_event_id: string}`. Only a currently pending, exactly project/run-bound report can receive its first human decision; the optimistic report update, history entry and linked verified-session audit event commit atomically, and an audit-write failure rolls all three back. `reason` is required except for `approved`. AI recommendation is not a human decision; no proposal permission or external execution follows from report approval.
- `GET /projects/{project_id}/reports/{report_id}/download?format=markdown|json` returns only a stored report Markdown artifact or a JSON serialization of the allowlisted `ReportDetail`; `Content-Disposition` uses a backend-generated safe filename. No request-supplied path is accepted. HTML, script content, unsafe links and Markdown images are removed/neutralized before Markdown display/download. Frontend Markdown renderers must still disable raw HTML and external image loading.

### Audit timeline

- `GET /projects/{project_id}/audit?page=1&page_size=25&event_type=...&since=...&until=...` and `GET /projects/{project_id}/audit/{event_id}` require a verified in-scope local session. The list returns `AuditCollection`: `{availability, items: AuditEvent[], total, page, page_size}`.
- `AuditEvent` is `{event_id, project_id, event_type, occurred_at, resource_type: string|null, resource_id: string|null, outcome, summary, actor_id: string|null, actor_verification: "verified_local_session"|"unknown", source}`. It projects persisted runs, report decisions, proposal decisions, dry runs, execution attempts, outbox receipts and security records only. Core/offline actors and legacy events without verifiable attribution have `actor_id: null` and `actor_verification: "unknown"`; timestamps are never treated as proof of authorship. The detail route returns the same DTO plus bounded, allowlisted `details: object`; token fingerprints and raw payloads are excluded.
- Capability: `audit:read`; access is not granted by a client role or actor claim.

### Weekly schedule, outbox and explicit manual cycle

- Weekly scheduler configuration is absent unless all server-only `H5_WEEKLY_SCHEDULE_PROJECT_ID`, `H5_WEEKLY_SCHEDULE_WEEKDAY`, `H5_WEEKLY_SCHEDULE_LOCAL_TIME`, `H5_WEEKLY_SCHEDULE_TIMEZONE`, and `H5_WEEKLY_SCHEDULE_WINDOW_RULE` settings are supplied and valid. The schedule model currently allows `timezone: "America/Guayaquil"` and `window_rule: "previous_scheduled_week"`. `H5_WEEKLY_CYCLE_ENABLED=false` by default. No automatic service trigger is probed or assumed: every schedule/config response uses `automatic_trigger_status: "not_verified"`.
- `GET /projects/{project_id}/schedule` → `ScheduleView`: `{project_id, availability: "configured"|"unknown", enabled, schedule: WeeklyScheduleView|null, planned_window: WeeklyWindowView|null, is_due: boolean|null, is_dispatched: boolean|null, outbox_history: "available"|"unknown", can_run_manually: boolean, last_receipt: OutboxReceiptSummary|null, automatic_trigger_status: "not_verified", remote: {required: false, server_allowed: false, availability: "not_checked", providers: []}}`. Missing schedule/records remain unknown. `WeeklyWindowView` contains the persisted scheduler's `window_id`, local/UTC start/end/cutoff and next-boundary timestamps.
- `GET /projects/{project_id}/schedule/outbox?page=1&page_size=25` → `OutboxCollection`: `{availability, items: OutboxReceiptSummary[], total, page, page_size}`. `GET /projects/{project_id}/schedule/outbox/{delivery_id}` → `OutboxDetail` (`receipt` plus allowlisted persisted `message`, no arbitrary file path). `GET /projects/{project_id}/schedule/outbox/{delivery_id}/download?format=markdown|json` serves only content bound to the stored receipt/message. File-backed receipts are downloadable only after exact configured outbox-root containment, regular-file, no-symlink, project/window/delivery and report/run binding checks; missing artifacts remain unavailable, never synthesized.
- `OutboxReceiptSummary`: `{delivery_id, message_id, project_id, window_id, channel, status: "DELIVERED"|"SKIPPED_DUPLICATE"|"FAILED", dispatched_at, artifact_available: boolean, report_id: string|null}`. Message fields are allowlisted `subject`, sanitized `summary`, sanitized `body_markdown`, persisted metrics/risks and report binding.
- Explicit manual execution uses two protected steps: `POST /projects/{project_id}/schedule/manual-cycle/prepare` JSON `{request_cycle: true}` → `ScheduleCyclePreparation: {preparation_id, project_id, expires_at, configuration_fingerprint, eligible, capabilities, preflight: {schedule_status: "configured"|"incomplete"|"invalid"|"disabled", window_id: string|null, has_captures: boolean|null, outbox_history: "available"|"unknown", report_binding: "available"|"unknown"|"mismatch", can_run}, remote: {required: false, server_allowed: false, availability: "not_checked", providers: []}}`; then `POST /projects/{project_id}/schedule/manual-cycle/confirm` with `Idempotency-Key` and JSON `{preparation_id, configuration_fingerprint, confirm_cycle: true, remote_consent: false}` → HTTP 202 `{job: WeeklyCycleJob, reused: boolean, poll_url: string, poll_after_ms: number}`. Preparation is session-, project-, schedule/config-, purpose- and expiry-bound. Confirm rejects changed config, missing current capture/report/run binding, missing outbox history, missing server opt-in, remote consent `true`, active queue saturation or conflicting idempotency. Execution uses the existing `WeeklySchedulerService` with channel `sqlite`, never `force`; it creates no snapshot or final AI report and invokes no remote provider/source or external delivery.
- `WeeklyCycleJob` is `{job_id, project_id, status: "queued"|"running"|"completed"|"failed"|"interrupted", created_at, updated_at, outcome: "EXECUTED"|"SKIPPED_NOT_DUE"|"SKIPPED_ALREADY_DISPATCHED"|"FAILED"|"unknown", window_id: string|null, delivery_id: string|null, error_code: string|null, remote_consent: false}`. Terminal statuses are `completed|failed|interrupted`; `completed` does not mean `EXECUTED` unless `outcome` says so. The paginated jobs list returns `{availability, items, total, page, page_size}`; the list and `GET /projects/{project_id}/schedule/manual-cycle/jobs/{job_id}` require verified in-scope session and capability `weekly_cycle:confirm`. One bounded worker and finite queue; GET polling does not write. Stale active jobs are projected as interrupted and persisted as interrupted on the next protected preparation.
- Capabilities are server-derived and only present for a verified session scoped to a configured project: `audit:read` and `configuration:read` are protected read capabilities; `governance:proposal_review`, `governance:dry_run_authorization`, `governance:dry_run`, `reports:decide`, `weekly_cycle:prepare`, and `weekly_cycle:confirm` are separately gated by their server-side feature flags. None permits external writes.

### Sanitized project configuration

- `GET /projects/{project_id}/configuration` → `ProjectConfiguration`: `{project_id, availability: "available"|"unknown", source_mode: "fixtures"|"real"|"stored", timezone: string|null, due_soon_days: number|null, repository: {configured, owner: string|null, name: string|null, branch: string|null, commit_sha: string|null}, trello: {configured, board_id: string|null, credential_status: "configured"|"missing"|"unknown"}, providers: ProviderPreflight[], policies: {configured: boolean|null, version: string|null}, schedule: WeeklyScheduleView|null, schedule_status: "configured"|"not_configured"|"incomplete"|"invalid", capabilities: string[], editable_fields: []}`. Secrets and raw settings, provider payloads, arbitrary config/artifact paths and credentials never enter the DTO. Provider/model and credential *presence* are metadata only; availability is not probed. Configuration is read-only (`editable_fields: []`).
- Server switches: `H5_GOVERNANCE_ENABLED=false`, `H5_REPORT_DECISIONS_ENABLED=false`, `H5_WEEKLY_CYCLE_ENABLED=false`; no client value overrides them. All three mutation families require Origin+CSRF, verified session, configured-project scope and idempotency. No external-call opt-in is exposed for proposal simulation or weekly cycles.
